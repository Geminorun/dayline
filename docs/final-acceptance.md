## 容量记录的解释

建议基线不是总量硬配额。脚本每次创建 20 个独立账号，**每个账号** 1,000 事项 / 10,000 重点状态，进行 5 轮 100 次完整快照和 100 次版本受控保存，记录完整字节、gzip 对照、JSON 解析 / 契约校验 / 初算和 RSS。服务器为本会话 5 可见 CPU / 约 17.59 GiB 内存，回环 HTTP，没有把它称为目标 2C / 4G 生产结果。

首轮完整读取 P95 2913 ms、保存 1624 ms，与备份短暂重叠；移除重点的 Prisma Date / 无用列物化后，独立一轮读取 1639 ms、保存 816 ms。进一步事项原生 JSON 聚合保持 RR / 完整图 / false / trash / UTC 日期语义，最终独立读取 P95 **1697.41 ms**、保存 P95 **847.24 ms**，一秒读取目标仍未达；完整测量参数与原始报告位置见 [stage7-handoff.md](stage7-handoff.md)。不以减少数据、隐藏字段或缓存伪完整快照达标。其间与受控时钟维护专项重叠的一轮因会话被测试过期扫描撤销而作废；维护专项现独立新建专用 `_test`，后续容量与恢复串行运行。

实际小程序滚动帧率、WebKit / Safari、iOS / Android、真实 Resend / 微信、小程序审核 / 发布、完整无障碍审计和目标机器压测仍 pending。没有发布或部署生产服务。
