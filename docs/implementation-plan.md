用户已授权连续完成下列七个阶段，不逐阶段等待人工确认。每阶段仅由一个新建的 GPT-6.1-Sol / high Agent 实现；主 Agent 制定任务、审查代码及验证证据，将问题交回该阶段原 Agent 修复。评审通过后由主 Agent 创建独立 Git 提交并推送 origin/work，随后启动下一阶段。实现 Agent 不自行提交、推送、发布或继续其他阶段。

完整需求与接口以 requirements.md、backend-spec.md、frontend-spec.md 及用户最新决定为准；保持两个独立前端、一个后端，在线保存、全量刷新和 Web 草稿手动提交，不引入 Redis 或离线同步引擎。

## 评审与交接

阶段完成时记录实现范围、检查结果、评审发现及修复、提交哈希和未执行的外部验证。阶段通过只表示约定范围及可执行检查通过，不表示产品已发布或尚未执行的人工测试已通过。

### 阶段 1 评审清单

- 两个独立前端、共享契约和传输客户端可分别构建；小程序输出必须是 mp-weixin，公共包不能夹带 DOM、uni 或服务端依赖。
- 网页邮箱流程有可操作页面、验证 / 重置失败状态、可信回跳及敏感 query 清理；密码不持久化。
- 无邮箱微信身份使用统一内部用户和受支持的签名会话；普通登录与扫码解析不泄漏内部标识。并发首登收敛到一个身份和用户。
- 无邮箱身份后续添加真实邮箱及密码保留用户 ID 的能力经过适配器级验证，不为测试开放生产后门。
- QR 浏览器、扫描者和确认凭据彼此隔离，状态及到期由服务器判定；resolve 不建未知用户，明确确认后才建号。
- QR 不允许未确认领取、跨浏览器领取、身份替换、取消 / 到期后领取和重复领取；绑定目的在阶段 6 前明确拒绝。
- 邮箱既有回归、真实 PostgreSQL 身份 / QR 集成测试、共享包测试、格式 / lint / 类型与双端构建提供实际结果。
- 真实微信交换与小程序码、真实邮件投递及设备测试的证据单列；缺少外部条件不冒充通过。

### 阶段 1 首轮发现（已修复并验证）

- R1：扫码确认前独立提交身份创建，会在取消 / 到期 / proof 轮换竞争中留下不应创建的账号；须统一事务并验证回滚。
- R2：微信登录应允许待注销账号取得受限会话以便后续撤销，不能比邮箱登录更严格地永久挡在登录外；仍拒绝已合并来源。
- R3：邮箱绑定技术原语须先规范化并严格验证，防止大小写 / 空白绕过内部保留后缀，并验证唯一性竞争回滚。
- R4：微信 code 无效与上游 / 配置失败须区分；真实小程序码图片不能把合法格式误判为接口失败，错误内容须脱敏。
- R5：共享客户端未知响应须运行实际 decoder，成功校验后才接收凭据；匿名登录失败不无条件清除现有私人账号上下文。
- R6：确认后的扫码者在浏览器领取前仍能取消；proof 仅保留于本次内存流程并在结束时清除，已消费状态要清楚反馈。
- R7：清理邮件回调 token 时保留 Vue Router 必需的 history 元数据，同时不在 URL / history state 留下 token。
