# 分阶段实施与评审记录

## 执行规则

用户已授权连续完成下列七个阶段，不逐阶段等待人工确认。每阶段仅由一个新建的 GPT-6.1-Sol / high Agent 实现；主 Agent 制定任务、审查代码及验证证据，将问题交回该阶段原 Agent 修复。评审通过后由主 Agent 创建独立 Git 提交并推送 origin/work，随后启动下一阶段。实现 Agent 不自行提交、推送、发布或继续其他阶段。

每阶段执行适用的格式、lint、类型检查、构建、自动化及集成验证。最终由用户统一人工验收。未具备凭据或设备的真实微信、真实 Resend 投递、iOS / Android 真机测试必须列为待验证，不用 mock 或编译结果冒充通过；可在可替换适配器下完成代码和自动化验证。涉及产品范围变更或无法解决的关键阻塞才向用户提问。

完整需求与接口以 requirements.md、backend-spec.md、frontend-spec.md 及用户最新决定为准；保持两个独立前端、一个后端，在线保存、全量刷新和 Web 草稿手动提交，不引入 Redis 或离线同步引擎。

## 评审与交接

阶段完成时记录实现范围、检查结果、评审发现及修复、提交哈希和未执行的外部验证。阶段通过只表示约定范围及可执行检查通过，不表示产品已发布或尚未执行的人工测试已通过。

### 阶段 1 评审清单

- 两个独立前端、共享契约和传输客户端可分别构建；小程序输出必须是 mp-weixin，公共包不能夹带 DOM、uni 或服务端依赖。
- 网页邮箱流程有可操作页面、验证 / 重置失败状态、可信回跳及敏感 query 清理；密码不持久化。
- 无邮箱微信身份使用统一内部用户和受支持的签名会话；普通登录与扫码解析不泄漏内部标识。并发首登收敛到一个身份和用户。
- 无邮箱身份后续添加真实邮箱及密码保留用户 ID 的能力经过适配器级验证，不为测试开放生产后门。
- QR 浏览器、扫描者和确认凭据彼此隔离，状态及到期由服务器判定；resolve 不建未知用户，明确确认后才建号。
- QR 不允许未确认领取、跨浏览器领取、身份替换、取消 / 到期后领取和重复领取；绑定目的在阶段 6 前明确拒绝。
- 邮箱既有回归、真实 PostgreSQL 身份 / QR 集成测试、共享包测试、格式 / lint / 类型与双端构建提供实际结果。
- 真实微信交换与小程序码、真实邮件投递及设备测试的证据单列；缺少外部条件不冒充通过。

### 阶段 1 首轮发现（已修复并验证）

- R1：扫码确认前独立提交身份创建，会在取消 / 到期 / proof 轮换竞争中留下不应创建的账号；须统一事务并验证回滚。
- R2：微信登录应允许待注销账号取得受限会话以便后续撤销，不能比邮箱登录更严格地永久挡在登录外；仍拒绝已合并来源。
- R3：邮箱绑定技术原语须先规范化并严格验证，防止大小写 / 空白绕过内部保留后缀，并验证唯一性竞争回滚。
- R4：微信 code 无效与上游 / 配置失败须区分；真实小程序码图片不能把合法格式误判为接口失败，错误内容须脱敏。
- R5：共享客户端未知响应须运行实际 decoder，成功校验后才接收凭据；匿名登录失败不无条件清除现有私人账号上下文。
- R6：确认后的扫码者在浏览器领取前仍能取消；proof 仅保留于本次内存流程并在结束时清除，已消费状态要清楚反馈。
- R7：清理邮件回调 token 时保留 Vue Router 必需的 history 元数据，同时不在 URL / history state 留下 token。

迁移验证采用新的专用 dayline_stage1_test 空库，保留旧测试库及其记录。新迁移按真实时间命名；不能通过修改已应用历史或绕过 Prisma 保护修复排序。

### 阶段 2 评审清单

- 默认分类与初始化标记同事务，邮箱 / 微信两条创建路径一致；SQL 与纯共享默认值一致，删除自定义后重登不补回。
- 精确日历日期、码点长度、分类归属、分类上限与最后一类、未来开始及北京时间结束规则按 Spec 验证。
- 内容 version、每日期重点 version、集合 focusVersion 与用户 dataVersion 各司其职；无变化不递增，重点不误增内容版本。
- 缩短范围的重点移除必须精确确认当前日期 / 版本列表；分类转移包含活动和回收站记录，并整笔原子提交。
- 每账号固定锁顺序及 CAS、稳定新建 ID、跨账号访问和 epoch / expected-user / Origin 保护，含真实业务 PATCH 的 uni 转发回归。
- 30 天到期不可恢复；清空须确认快照版本，部分清理任何冲突整体失败，不因旧请求复活已永久删除记录。
- 快照一致完整、含 false 重点与回收站，无静默截断；ETag 含用户 / 版本 / 日期，先鉴权后 304，私有缓存头正确。
- 网页真实录入回看不假保存，复杂交互需要组件 / 浏览器验证；既有邮箱微信扫码与双端构建不回归。

### 阶段 2 首轮发现（已修复并验证）

- S2-R1：未发布的新迁移使用未来时间名，可能使后续依赖倒序。改为真实 UTC 命名，保留旧试验库，最终迁移 20261026162718_record_core 使用显式事务，新建 dayline_stage2_final_test 与 dayline_stage2_final_empty_test，验证空库全链及带已有用户的旧链升级；不 reset、不改已应用历史。
- S2-R2：业务错误码 / 状态与 Spec 15.1 漂移，最后分类的检查顺序使 LAST_CATEGORY 不可达。统一稳定契约并补分类、语义输入和最后分类回归。
- S2-R3：写入返回 meta.dataVersion，但共享客户端丢弃 meta，无法供后续缓存阻止旧快照覆盖。校验并保留 ApiMeta、补 OpenAPI，快照 Vary 合并现有 Origin。
- S2-R4：单事项 10,000 重点的精确移除确认超过普通 64 KiB，合法预览无法提交。使用仅匹配事项 PATCH（含 uni 转发）的有界专用 JSON 解析，并验证大列表、精确确认和普通 / 原生请求限制不回归。
- S2-R5：未初始化用户不得取得 complete:true 空 / 半份业务数据或写入成功；集中就绪检查保留认证恢复通道，并覆盖异常标记场景。
