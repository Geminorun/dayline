## 1. 背景与目标

现有日序是通过 ChatGPT Sites 发布的生活记录工具，提供事项日期区间、每日回看、每日重点、分类、时间轴和跨设备同步等功能。现站的身份认证、托管和云端数据存储依赖平台服务。

新版本面向更多用户，保留现有产品的核心体验，将账号、业务接口和数据存储部署在自有服务器上，增加微信小程序入口。普通记录和同步操作不依赖 ChatGPT 登录或 ChatGPT 后端。

### 1.1 产品目标

已确认产品定位：记录持续的经历、回看每天的重点。首版以经历回顾为核心，待办管理、提醒和重复任务不纳入核心范围。

1. 用户可以记录一段持续数天、数周或数月的经历，例如读书、游戏、运动和工作项目。
2. 用户可以按日期回看当时正在做的事，并标记属于某一天的重点。
3. 同一用户在小程序和网页中访问同一份记录，修改可以同步。
4. 不同用户的记录相互隔离；多人使用不意味着共享彼此的生活记录。
5. 产品可独立部署、备份和迁移，日常运行不依赖原站托管平台。
6. 将网页和小程序的界面分别维护，同时复用日期计算、数据校验和接口定义。

### 1.2 需求来源与证据边界

- 现有功能以原站第 9 版发布记录对应的源码为参考；本次调研没有完成实际浏览器交互体验。
- 原版已有的游客保存、账号隔离、离线同步和冲突处理测试共 7 项，通过了本地运行验证；这些结果不代表新版本已实现或通过验收。
- 本文中“已确定”表示用户确认的方向；“工程建议”“首版建议”及具体参数不等于用户逐项确认或实现已通过验证；需细化和验证的事项集中列在第 12 节。
- 同一决策以后续确认为准。第 25 题 A 及后续确认已调整原第 3 题的离线自动同步要求，以及第 24 题中“之后增量同步”的实现方式；当前方案以第 7 节为准。
- 当前聚焦代码、业务规则和技术方案。域名及服务器可以更换，已知资源仅作背景记录，不作为业务代码约束，也不作为继续需求访谈的阻塞项。

## 2. 已确定的方案

| 决策 | 内容 |
| --- | --- |
| 产品定位 | 记录持续的经历、回看每天的重点 |
| 产品形态 | 电脑网页与微信小程序，共用账号和数据；完整手机网页不作为首版要求 |
| 已登录账号的保存方式 | 在线调用后端，服务器确认后显示已保存；Web 断网可查看已加载缓存、暂存草稿，恢复网络后由用户手动提交，不自动补传 |
| 小程序网络范围 | 按在线应用设计，不要求已登录账号的离线记录或离线同步；游客本机体验仍按已确认规则提供 |
| 游客使用 | 网页与小程序均可不登录使用完整本地业务功能；记录存于本机，登录时按规则接入账号 |
| 游客数据接入 | 云端无业务数据时直接接入本机记录；云端已有数据时先预览合并，默认保留双方不同内容；服务器确认成功前保留本机原数据 |
| 缓存恢复 | 同一微信或邮箱身份重新登录后可取回服务器已确认的数据；换设备不新建业务账号，空缓存不触发云端删除 |
| 加载与刷新 | 首次完整加载账号业务数据；之后在线全量刷新。保存时立即调用后端，回前台或恢复网络立即拉取，持续前台约每 30 秒检查更新 |
| 开放方式 | 首版直接开放注册，不采用邀请或试用名单作为公开使用的前置条件 |
| 数据交换 | 首版支持 CSV 导入导出；带当前账号原记录 ID 的行可更新，无 ID 的行作为新增候选；文件缺少某条记录不会删除原记录 |
| 删除恢复 | 事项删除后进入回收站保留 30 天，期间可恢复或经确认提前清空 |
| 日期规则 | 首版统一北京时间 Asia/Shanghai，不随服务器或设备所在时区改变“今天” |
| 视觉方向 | 延续原站记录布局；Web 保留青绿默认主题，增加 GitHub、VS Code、Cursor、Notion、护眼、米黄预设、明暗 / 跟随系统及自定义主题色，外观按设备保存 |
| 完整备份 | 首版同时支持 CSV 和完整 JSON 导入导出；JSON 保留恢复所需的结构及版本元数据 |
| 原站迁移范围 | 首版从空数据开始，不建设原站专用迁移工具；通用 CSV 导入导出仍属于首版 |
| 后端 | 一套统一后端，提供认证、用户、事项、分类、重点、完整读取及版本校验接口 |
| 前端组织 | 两个独立前端工程，公共业务代码放入共享包 |
| 代码仓库 | 一个仓库管理前端、后端和共享包 |
| 登录方向 | 网页使用完整邮箱密码流程，并保留小程序扫码确认登录；小程序使用基础微信登录，绑定后访问同一账号 |
| 认证实现 | Better Auth 集成现有后端，网页认证表单自行实现；不增加独立的 Logto 认证服务 |
| 邮件发送 | 原无现成邮件渠道；选用 Resend 发送邮箱验证和密码重置等事务邮件，实际投递尚待验证 |
| 账号注销 | 两端支持自助申请，7 天内可撤销，到期后清理账号及业务数据；与事项 30 天回收站分开处理 |
| 小程序时间轴 | 首版提供完整横向时间轴，支持月、季度、年及全部时间范围，按手机交互适配 |
| 身份关联 | 两端关联同一内部用户 ID，不将 UnionID 作为首版运行前提 |
| 账号冲突处理 | 登录切换、绑定与合并分开；已有两账号时验证双方、预览后合并，默认保留双方；也可暂不绑定 |
| 托管方式 | 后端、数据库和网页静态资源部署到自有服务器；小程序通过微信平台发布 |
| 小程序接入 | 计划使用个人主体；通过标准 HTTPS API 直接接入统一后端，不依赖 CloudBase AnyService 或 uniCloud |
| 服务端存储 | PostgreSQL；首版不加 Redis，不建离线队列或增量同步日志表；普通记录保留稳定 ID 和版本检查，导入及账号合并保留自身幂等执行记录 |

### 2.1 技术栈基线与验证边界

两个独立前端、一个后端、共享业务包，以及 Better Auth、Resend 和 PostgreSQL 的选择已按讨论收敛。其余库沿用此前推荐的工程基线，不要求逐项投票；具体版本、认证模型和兼容性通过最小集成验证后固定，尚未初始化应用工程。

| 部分 | 选型 |
| --- | --- |
| 网页端 | Vue 3、TypeScript、Vite |
| 微信小程序 | uni-app、Vue 3、TypeScript |
| 后端 | Node.js、NestJS、TypeScript |
| 认证 | Better Auth，集成后端；已确认 |
| 数据库 | PostgreSQL；首版唯一服务端持久数据库，不使用 Redis |
| 数据库访问与迁移 | Prisma |
| 网页本机存储 | 少量草稿可用 localStorage；完整数据缓存建议使用 IndexedDB，均通过网页适配层访问 |
| 小程序本机存储 | uni-app / 微信本地存储，保存游客数据及必要缓存；不建设登录账号离线补传队列 |
| 事务邮件 | Resend；已确认 |
| 仓库管理 | pnpm workspace |

生产采用 GitHub Actions 构建发布，Web 与 API 合并为一个 Docker 镜像，复用现有 PostgreSQL 17 容器；初始化时仅在专用库 / 角色不存在时创建。HTTPS 默认复用本机 Nginx / 证书，入口容器为显式可选项；橙云开启并使用 Full (strict)，操作细节见 [部署指南](deployment.md)。业务逻辑不绑定域名、供应商或机器规格。首版不增加微服务、WebSocket 推送、Redis 或专用离线同步引擎。

### 2.2 工程边界

```text
dayline/
├── apps/
│   ├── web/          # 网页界面、浏览器登录和平台适配
│   ├── miniapp/      # 小程序界面、微信登录和平台适配
│   └── api/          # 认证、权限、业务接口、版本校验和数据库访问
├── packages/
│   ├── core/         # 日期、持续天数、重点日期等通用业务计算
│   ├── contracts/    # API 数据类型、请求和响应格式、通用校验规则
│   └── api-client/   # 公共 API 调用逻辑，通过适配器使用各端网络能力
└── docs/
```

- 共享包不直接依赖浏览器 DOM、微信全局对象、平台存储或数据库运行环境。
- 浏览器请求、小程序请求、本地缓存、文件导出和登录会话处理分别在客户端适配层实现。
- 页面布局和交互归各自前端所有；颜色、间距、分类配色等设计规范保持一致。
- 后端可以复用公共校验规则，但必须独立验证权限和输入，不能信任前端校验结果。
- 微信密钥、数据库凭据和后台专用代码仅存在于后端运行环境。
- 两个客户端独立构建和发布；后端升级须兼容仍在使用的旧版小程序。
- 两个前端共享日期、校验、API 契约和可复用业务规则；缓存、草稿、生命周期、请求与会话由平台适配器处理，不为跨端复用强行共用页面。
- 首版不增加独立的离线队列或增量同步共享包。后端按认证、账号关联、事项、分类、重点、导入导出和注销划分模块，保持一个应用。

## 3. 用户与使用场景

### 3.1 用户角色

| 角色 | 权限与行为 |
| --- | --- |
| 未登录访问者 / 游客 | 完整使用本机事项、分类、重点、回看、搜索、统计、时间轴和回收站；网页可对本机数据导入导出，登录后接入账号 |
| 已登录用户 | 管理自己的事项、分类和每日重点，跨端回看和同步，导入导出自己的数据 |
| 服务运营者 | 部署、备份和维护服务；首版不要求建设独立运营后台 |

### 3.2 核心场景

1. 用户在小程序新建“阅读某本书”，填写开始日期并将结束日期留空；之后每天都能回看到这段持续中的经历。
2. 用户在某一天将读书事项标为当天重点；其他日期的重点状态保持独立。
3. 用户在电脑网页扫描小程序码并确认登录，查看与手机相同的事项和宽屏时间轴。
4. 用户在网页结束一件事项，小程序更新后显示相同的结束日期。
5. 已登录用户在网页编辑时断网，输入暂存为草稿；恢复网络后先刷新最新记录，再由用户手动提交，发生版本冲突时保留草稿并明确处理。
6. 用户在网页下载 CSV 模板、整理自己的记录并导入，确认预览后在两端查看；也可导出自己的记录到 CSV。
7. 用户不登录也能在任一端记录经历；登录时，云端为空则直接接入本机记录，已有数据则先预览合并。
8. 用户更换手机，在同一个日序小程序中使用原微信身份登录，重新加载服务器已确认的数据。
9. 用户自行申请注销，7 天内可以验证身份并撤销，未撤销的申请到期后清理。

## 5. 账号与登录需求

### 5.1 统一用户身份

- 系统为每位用户生成内部 `user_id`，业务数据归属于该 ID。
- 微信身份记录至少包含应用标识、OpenID 与内部用户 ID 的关联；同一应用下相同 OpenID 不得重复创建用户。
- UnionID 如可合法取得，可以保存以支持后续账号关联；为空时不影响首版小程序登录和扫码确认登录。
- 后端通过微信登录凭证交换结果确认身份，不接受前端直接声明的 OpenID 或用户 ID 作为登录依据。
- 基础登录不以获取手机号、昵称或头像为必要条件；显示名称可以由用户自行填写。
- 用户切换账号后，不得继续显示前一个账号的缓存或未提交记录。

### 5.2 小程序登录

1. 用户在小程序发起登录。
2. 小程序获取微信临时登录凭证并提交给后端。
3. 后端调用微信接口校验凭证，获取当前小程序身份。
4. 后端查询或创建对应的内部用户，建立本系统会话。
5. 小程序完整加载该用户的数据，展示登录、加载和保存状态。

异常要求：凭证失效、微信接口不可用或服务暂不可用时，显示可理解的提示并允许重新发起；不能因重试产生重复用户。

### 5.3 网页扫码确认登录

该流程由日序后端协调，以小程序中已验证的身份确认网页会话，不以开通“网站应用微信 OAuth 登录”为前置条件。

1. 网页向后端申请一次登录请求，后端生成随机、短时有效的标识，并绑定发起请求的浏览器会话。
2. 网页展示携带该标识的小程序码，同时展示等待、过期和刷新状态。
3. 用户用微信扫描后进入日序小程序；未登录时先完成小程序登录。
4. 小程序明确展示“确认登录日序网页”，允许确认或取消；扫描本身不等于同意登录。
5. 后端验证小程序用户会话及登录请求状态，记录确认结果。
6. 发起请求的网页取得结果，后端为该浏览器建立新的登录会话，网页加载同一用户的数据。

首版建议参数与约束：

- 登录请求默认 2 分钟有效，可配置；过期后必须重新申请。
- 登录请求只能成功消费一次，取消、过期、重复确认都应有明确状态。
- 二维码只携带临时请求标识，不包含用户登录令牌或微信密钥。
- 确认结果只能被原浏览器会话领取，不能凭二维码中的标识领取他人的网页会话。
- 退出网页登录只结束当前网页会话，不应自动让其他设备退出。
- 手机浏览器无法直接扫描自身屏幕上的码，不能将此流程直接当作完整手机网页登录方案；完整手机网页已确定不作为首版要求。

### 5.4 小程序接口与平台边界

- 小程序计划使用个人主体，尚未注册；首版依赖基础微信登录，不假定已获得网站应用登录、手机号或 UnionID 相关权限。
- 小程序通过 uni-app / 微信请求适配器调用统一后端的标准 HTTPS API，不采用 CloudBase AnyService 或 uniCloud 作为业务后端前提。
- 接口地址、微信应用标识及后端凭据按环境配置，密钥仅存在后端；客户端不写死域名或服务器信息。
- 平台账号和发布条件在部署阶段核实，不在本轮代码与技术方案中继续展开；正式微信登录与小程序码尚未完成实际集成验证。

### 5.5 网页邮箱密码认证与 Better Auth（已确定）

用户已选择完整邮箱密码流程，由 Better Auth 集成后端提供标准认证能力，网页界面自行实现。

- 网页用户可使用邮箱独立注册，无需先开通微信账号或进入小程序。
- 首版包含注册、邮箱验证、验证邮件重发、密码登录、忘记密码、重置和修改密码、登录会话及退出。
- 未验证邮箱的用户进入验证引导，完成验证后才能使用该邮箱身份访问私人业务数据。
- 保留微信小程序扫码登录；邮箱身份和微信身份按第 5.6 节明确绑定或合并，不默认自动识别为同一人。
- 邮箱验证码免密码登录和独立 Logto 服务不作为本轮选定方案；如后续需要，再单独提出变更。

实现分工：

| 部分 | 放置位置与可复用能力 | 本项目仍需完成的部分 |
| --- | --- | --- |
| Better Auth | Node.js 后端的认证模块，提供标准邮箱密码、邮箱验证、重置密码和会话接口；有 Vue 客户端及 Prisma 适配 | 安装配置与版本验证、认证路由和邮件发送接入；NestJS 适配由社区维护，需检查所选组合 |
| 网页端 | 使用认证客户端或 HTTP 接口，保持前后端独立工程 | 注册、登录、验证结果、重发、找回与重置密码等页面及错误提示 |
| 微信与业务模块 | 复用统一用户归属与业务 API | 小程序登录、扫码确认、账号绑定及数据合并、业务权限与本机缓存 / 草稿隔离 |

组件选择已经确定，具体适配版本和微信身份映射方式通过最小集成验证后固定；验证尚未执行，不能将选型确认视为技术验证已经通过。

架构与实现边界：

- 认证逻辑属于后端，网页只处理界面并通过 SDK 或 HTTP 接口交互；不要求采用 uni-app 或 uniCloud 的云端一体方案。
- 前后端可以独立开发与构建；生产环境可将网页和 `/api` 反向代理到同一站点，简化网页登录 Cookie 的处理，工程拆分不要求公网域名也拆分。
- Better Auth 提供接口和客户端，不等于已交付日序风格的 Vue 登录页面。注册、登录、验证结果、忘记密码和重置密码等界面仍需实现或采用兼容模板。
- 通用认证组件处理账号凭据和会话；事项所属用户、接口访问权限及各账号缓存与草稿隔离仍由日序负责。
- 小程序不使用浏览器页面或直接假定支持浏览器 SDK；通过平台网络和会话适配调用后端。微信基础登录、扫码确认和两种身份的关联需单独实现并验证。
- 截至本轮调研，Better Auth 的 WeChat 文档位于 v1.8 Beta，明确针对网站应用 OAuth，不可将其视为当前小程序 `wx.login` 与自建扫码流程的现成替代。
- 全面实现前先验证最小流程：邮箱注册和验证、登录与业务接口鉴权、密码重置、小程序身份关联，以及退出或重置后的会话处理；未完成验证前不承诺装包即可覆盖全部双端认证。

共同要求及设计约束：

- 事务邮件选用 Resend，由后端邮件适配层接入 Better Auth 的发送回调，覆盖邮箱验证、重发和密码重置。处理发送间隔、有效期和发送失败，不能假定即时送达；当前未执行真实投递验证。
- 账号绑定同时验证当前登录身份和待绑定身份，不能根据用户输入的邮箱文字直接关联。
- 微信账号和邮箱账号若已经分别有数据，不按昵称或客户端声明自动合并；明确提示并通过单独设计的确认流程处理。
- 登录后允许维持会话，正常回访不需要每次重新输入密码或收取验证码；会话期限后续设计。
- 认证库与邮件渠道已确定为 Better Auth、Resend；会话期限、邮件参数及具体适配版本由技术设计固定，不引入独立托管认证平台作为运行前提。
- 最小集成验证必须覆盖没有邮箱的微信用户，确认 Better Auth 认证用户与内部业务用户是否能直接复用。必要时通过受控映射分离，不能伪造已验证邮箱，也不能要求所有微信用户先补邮箱才能使用。

### 5.6 登录、绑定与账号合并

本节的交互与数据保留策略已由用户确认，纳入首版。邮箱采用独立注册的完整密码流程，认证组件为 Better Auth；统一账号的选择、额外登录标识边界及映射实现仍需细化。

操作意图必须明确区分：

| 操作 | 用户意图 | 允许发生的变化 |
| --- | --- | --- |
| 登录或切换账号 | 进入某一已验证身份对应的账号 | 建立或切换当前客户端会话，不改变账号关联和数据归属 |
| 绑定登录方式 | 给当前账号增加另一个已验证的登录入口 | 未被占用的身份关联到当前账号；若身份属于其他账号，进入单独冲突流程 |
| 合并账号 | 将已确认由本人控制的两个账号统一 | 经过预览和明确确认后，迁移允许迁移的身份及数据，保留审计和恢复所需信息 |
| 刷新记录 | 同一账号在多个设备查看已保存修改 | 按第 7 节完整读取及检查记录版本，不作为重新注册、绑定或账号合并 |

#### 5.6.1 场景与处理规则

| 场景 | 处理规则 |
| --- | --- |
| 邮箱首次注册，微信尚未使用 | 先创建邮箱账号；从账号设置发起绑定后，将已验证且未被占用的微信身份直接关联到该账号 |
| 小程序先创建微信账号，再添加尚未使用的邮箱 | 验证邮箱后绑定到现有账号，并为该邮箱登录方式设置密码，不创建第二份业务账号 |
| 绑定码带用户首次进入小程序，微信尚无账号 | 先识别绑定意图并验证微信身份，确认后直接关联网页账号，避免先创建无意义的空账号再合并 |
| 网页和小程序都属于同一内部用户 ID，但记录数量不同 | 重新拉取完整服务器数据并保留当前编辑草稿；不显示两份账号数据的取舍弹窗 |
| 网页账号 A 绑定微信，微信已属于账号 B，只有一边有业务数据 | 核实双方身份并明确确认统一账号；保留已有业务数据。空账号判断还须考虑自定义分类、重点等内容，不能只看事项数 |
| 网页账号 A 与微信账号 B 都有数据，用户发起绑定 | 提示身份已关联到另一账号，完成双方验证后预览两边数据和冲突，提供“合并并保留双方”与“暂不绑定” |
| 网页已登录 A，却在登录页使用属于 B 的微信确认登录 | 这是账号切换，提示将进入 B；先处理 A 的待提交修改，确认后切换，A 与 B 的记录分别保留，不自动合并 |
| 绑定的邮箱已经属于另一账号 | 不覆盖邮箱关联；验证两个账号后按同一合并规则处理，无法验证另一账号时不允许迁移其身份或数据 |
| 微信或邮箱身份已经关联当前账号 | 提示已绑定并继续使用，不重复创建用户或绑定记录 |
| 重复邮箱注册、忘记密码或邮箱未验证 | 进入对应的登录、验证邮件重发或密码恢复流程，不另建同邮箱账号，不改变原有记录 |
| 扫错账号、请求过期或取消操作 | 结束本次操作，双方账号和数据保持原状，不产生绑定或合并 |

说明：只有验证相关账号控制权后才能展示该账号的记录概要，不能凭输入的邮箱或未完成的扫码请求展示他人的数据。

#### 5.6.2 用户举例对应的界面示例

当网页已登录邮箱账号 A，用户希望与微信小程序同步时，入口文案为“绑定微信”，生成专用于绑定的二维码；登录页的“用微信登录”使用另一种请求意图，后端分别校验，不根据前端按钮文案判断操作性质。

若扫描后发现微信对应另一个账号 B，且双方都有数据，在完成必要身份验证后展示类似内容：

```text
这个微信已有日序账号，是否与当前邮箱账号合并？

当前邮箱账号：20 条事项、3 个分类、30 个重点日
微信账号：    8 条事项、2 个分类、12 个重点日

合并后可以用邮箱或微信进入同一账号。
合并前会预览重复和冲突记录，默认保留双方的不同内容。

[预览合并]  [暂不绑定]
```

数量仅为示例，不代表合并后可以直接相加。账号空数据或新身份也应让用户确认绑定，但不要求其在两份数据中做选择。

#### 5.6.3 数据合并规则

- 默认保留双方独有的事项和重点关联。不同账号中的同名事项不自动判为重复。
- 能证明属于同一记录且内容完全相同时可去重；同一记录 ID 的内容不同、又没有可靠共同基准时，首版保留两份并生成新的唯一 ID，不用更新时间直接覆盖。
- 分类名称和颜色都相同可复用；名称相同但颜色或含义不同则保留并明确区分，事项及重点关联必须跟随映射。
- “暂不绑定”表示网页继续使用 A、小程序继续使用 B；两边数据独立保留，尚不互通。
- 首版不提供“保留整份 A 并删除 B”的快捷按钮；如果后续提供舍弃某份数据的能力，需要独立的备份、预览及删除确认流程。
- 账号有两个不同邮箱或多个微信等额外登录标识时，不能默认认证库支持全部移入同一账号；超出首版可支持的组合应明确拒绝合并或另行设计。

#### 5.6.4 合并期间和合并后的约束

- 登录组件可以复用通用凭据和会话能力，但不会自动合并日序的事项、分类与重点日期，需要单独实现账号归属迁移。
- 合并必须在线执行；当前设备存在未提交草稿时先手动提交或另行保留，不能自动提交。操作前保存可恢复快照，预览与执行之间发生数据变化时重新检查版本。
- 合并请求可重试且幂等，执行成功前不将账号对外显示为已合并；失败不能留下仅迁移部分身份或业务记录的状态。
- 绑定关系具有唯一性；执行前再次检查身份未被并发操作绑定，不能移动到未授权的账号。
- 保留受控的来源账号到统一账号及记录 ID 的映射；统一账号的选择和可迁移登录标识在技术设计中固定。
- 合并完成后刷新或重新建立会话、重新加载数据，旧会话需要失效或被安全更新，不能继续按过时归属写入。
- 其他网页可能仍有来源账号的未提交草稿，不能直接清空。重新认证并取得后端确认的合并映射后，关联到正确记录、拉取最新版本并检查删除状态，再由用户手动提交或处理冲突；不恢复自动补传队列。
- 上述受验证的合并映射是账号切换规则的特殊情况；普通切换账号时仍禁止把旧账号的草稿或记录提交给新账号。

### 5.7 游客完整使用与登录后接入

- 网页和小程序均可不登录使用事项、分类、每日重点、回看、搜索、统计、完整时间轴及本机回收站；网页提供本机数据的 CSV / JSON 导入导出。跨设备共享、账号绑定与注销需要登录。
- 游客数据保存到独立的本机命名空间，与每个登录账号的缓存和草稿分开；本机保存成功才能提示成功，容量不足或写入失败不得伪装成已保存。
- 游客本机记录不依赖服务器，不等于已登录账号支持离线同步；小程序仍不承诺断网启动或完整离线运行。游客缓存清除且未导出或上传时，不能自动找回旧数据。
- 登录后先检查云端：没有用户创建的业务内容时直接接入本机记录；仅有系统默认分类不视为已有私人数据。不能只看事项数，还需检查重点、自定义分类及回收站等内容。
- 云端已有业务数据时，验证身份后先展示本机 / 云端概要及合并预览，默认保留双方不同内容。可以暂不导入，继续使用云端账号；暂不导入不删除游客原始数据。
- 同名事项不自动去重；分类匹配、记录 ID 差异和重点关联遵循保留双方及明确映射的规则。游客接入是本机数据导入，不是两个云端身份的自动合并。
- 接入使用稳定的导入标识并可幂等重试；服务器确认全部完成后才标记已导入。失败、中断或确认响应丢失时保留原始本机数据，重试不能重复生成记录。

### 5.8 自助注销与 7 天撤销窗口

- 两端提供自助注销入口；申请前重新验证当前身份，说明清理范围为该统一账号的业务数据和关联登录方式。
- 注销申请由服务器确认后进入连续 7 天的撤销窗口，展示具体到期时间；窗口内验证身份后可明确撤销，普通登录不应无提示取消注销。
- 到期未撤销时执行账号及业务数据清理，撤销有效会话和身份关联；清理任务必须可重复执行。账号状态保存在 PostgreSQL，定时扫描不依赖 Redis。
- 事项 30 天回收站与账号注销分开：已注销账号不能通过恢复事项或旧客户端提交复活。未提交草稿应允许另行保留，但不自动迁移到新注册账号。
- 工程建议：待注销期间仅允许验证、撤销、导出和退出等必要操作，暂停业务写入、绑定与合并；具体状态和会话处理在第 12 节固定，不视为用户额外选择。
- 服务端历史备份按既定保留周期淘汰，不承诺所有备份副本在注销到期的同一时刻消失。

## 6. 核心功能与业务规则

### 6.1 事项管理

每件事项包含名称、开始日期、可选结束日期、分类及每日重点关联。

| 字段或操作 | 规则 |
| --- | --- |
| 事项名称 | 必填，去除首尾空白后为 1–100 个字符 |
| 开始日期 | 必填，合法的日历日期，允许未来日期 |
| 结束日期 | 可空；填写时不得早于开始日期 |
| 分类 | 必须属于当前用户且仍然有效 |
| 新建 | 游客写入本机成功后进入对应视图；登录账号在服务器确认后保存成功，Web 未提交输入仅显示草稿状态 |
| 编辑 | 更新名称、日期和分类，不改变事项身份；日期调整涉及重点日期时按第 6.3 节处理 |
| 结束 | 将结束日期设为账号当前日期；未来才开始的事项不能直接执行“今天结束” |
| 删除 | 二次确认后将整件事项及其重点关联移入回收站，从正常视图隐藏并同步到其他客户端，保留 30 天恢复窗口 |

事项状态由日期计算，不要求用户每天手工更新：

- 已结束：已填写结束日期，且结束日期早于或等于今天。
- 进行中：结束日期为空或晚于今天，包括未来开始的记录；不再单列“未开始”。

日期跨度包含开始与结束当天。有结束日期时按完整区间计算总跨度；无结束日期且已经开始时计算到今天。未来事项以开始日期作说明，不能展示负数或声称已经持续；只有进行中、已结束两个状态，默认筛选进行中。

#### 6.1.1 回收站与恢复

- 删除事项后，正常列表、每日回看、时间轴及统计不再包含该事项；回收站保留其字段和重点日期。
- 登录账号的保留期从服务器确认删除的时间起计算 30 天；断网不能执行已确认的删除，也不排队自动补传。游客本机删除从本机保存成功时计时，由客户端运行时处理到期清理。
- 期限内可恢复，恢复后的事项和重点重新出现在对应视图，恢复结果同步到其他客户端。
- 用户可提前清空回收站，执行前再次确认不可通过回收站恢复；到期后由服务自动清理。
- 分类删除时，回收站中引用该分类的事项关联到“其他”，原期限不变，恢复时分类有效。
- 其他端在下次完整刷新后反映删除或清理。旧缓存不能反向整份覆盖服务器；草稿目标已删除或已清理时，提交必须提示，不将旧编辑自动当作新增或恢复。
- 删除、恢复与编辑发生并发时检查版本；其他端的旧删除操作不能覆盖刚恢复的记录，旧编辑也不能直接恢复已删除记录。

### 6.2 每日回看

- 支持选择今天和历史日期，查看覆盖该日期的事项。
- 已结束事项的覆盖范围包括开始和结束当天；未填写结束日期的事项从开始日期持续显示到今天。
- 未来日期允许浏览，但不能将尚未发生的一天标为每日重点。
- 支持前一天、后一天、回到今天及日历选择；小程序使用适合手机的日期导航。
- 显示当天事项、进行中事项及涉及分类的数量；统计范围须清楚标注为当天或全部。
- “当天覆盖过的事项”与“今天是否仍在进行”分别计算，历史回看不得因事项后来结束而丢失记录。

### 6.3 每日重点

- 重点属于“事项 + 日期”，不能只为整件事项保存一个全局星标。
- 同一事项同一天最多有一个重点标记，支持取消和补记历史日期。
- 重点日期必须在事项的有效日期范围内，且不得晚于账号当前日期。
- 每日回看中显示该日重点，事项详情可查看累计重点天数和具体日期。
- 缩短事项日期范围会移除部分重点时，须列出受影响日期并让用户确认，不能静默丢弃。
- 不同设备为同一事项添加不同重点日期时，应保留两端结果；重点日期去重。

### 6.4 分类管理

- 新用户默认拥有游戏、阅读、工作、运动、生活、其他六个分类，沿用原站的初始配色。
- 支持新增、修改名称、修改颜色和删除分类。
- 首版建议沿用原站前端限制：名称 1–12 个字符，每位用户最多 20 个分类；同一用户不允许重复分类名。
- 至少保留一个分类；删除最后一个分类时提示先添加其他分类。
- 删除分类时展示影响数量并确认，将活动事项移入 30 天回收站；已有回收站事项保留原到期时间。分类本身删除，事项仍能恢复，恢复后归入“其他”，不永久清理记录。至少保留一个分类。
- 分类标签支持左右拖动排序，也支持键盘操作；游客保存在本机，账号顺序在各端共享，新分类追加到末尾。
- 分类名称和颜色修改后，相关事项的显示同步更新。

### 6.5 搜索与筛选

- 支持按事项名称搜索，按分类和状态筛选，并提供一键清除筛选。
- 状态只有进行中、已结束，默认进行中；清除其他筛选也恢复该默认值。
- 支持按开始日期升序或降序排列。
- 无数据与筛选后无结果采用不同提示，避免让用户误以为记录被删除。
- Web 在每日回看和时间轴内提供搜索、分类和状态筛选；完整历史可在时间轴选择全部时间。小程序的全部记录和时间轴使用一致的搜索及筛选规则。

### 6.6 时间轴与统计

网页端：

- 支持月、季度、年和全部时间视图，以及前后切换和定位今天。
- 以横条展示事项跨度，未结束事项延伸到今天；未来事项保留计划日期说明。
- 展示重点日期，较大时间范围按周或月汇总；可进入查看具体日期。
- 点击事项可查看或编辑，保留筛选和当前浏览位置。
- 长时间范围、较多事项采用合适的分页或按需渲染方式，避免一次渲染全部元素导致卡顿。

小程序端：

- 已确认首版提供完整横向时间轴，不以精简列表替代时间轴范围浏览。
- 支持月、季度、年及全部时间范围切换、前后移动和定位今天；展示事项起止、状态、跨度及重点日期。
- 支持横向滚动查看日期，纵向查看事项；事项名称保持可识别，避免日期滑动后失去对应关系。
- 大范围按周或月汇总重点，支持查看具体重点日期；可进入事项详情并编辑。
- 提供与网页一致的搜索、分类和状态筛选规则；触控区域、标签密度和弹窗按手机尺寸设计。
- 时间轴计算、事项范围和重点日期规则与网页一致，渲染及性能适配在小程序前端单独实现。

基础统计按所选范围展示事项总数、进行中数量、涉及分类数量和分类分布。分类分布按事项数量统计，每件事项计一次，不能让用户误解为时间投入占比。

### 6.7 CSV 导入导出与数据备份

通用 CSV 导入导出为已确认的 P0：

- 网页游客导入导出当前本机游客数据，登录账号导入导出服务器已确认的数据；共享格式和预览规则。下文“当前账号”在游客模式下对应当前本机命名空间，文件不因此具有云端身份权限。
- 网页提供可下载的 CSV 模板和填写示例；具体列定义在接口与导入设计中冻结。
- 支持导入事项名称、开始日期、可选结束日期、分类和重点日期；分类颜色、稳定记录 ID 等扩展列在模板设计时明确。
- 模板使用 UTF-8，明确日期格式与多重点日期的表示方式；导出兼顾常见表格软件的中文显示和 CSV 转义规则。
- 上传后先校验，按行展示错误原因及新增、重复、冲突记录的数量；用户确认后才写入数据。
- 已确认 CSV 支持批量新增和更新：记录 ID 匹配当前账号原记录时作为更新候选，无 ID 的行作为新增候选。
- 导出提供稳定记录 ID，并保留检查更新冲突所需的版本信息；用户修改 CSV 后再次导入，可在预览中看到新增和更新的字段。
- 同一账号重复导入同一文件时不应生成重复记录；无 ID 的疑似重复项在预览中明确处理，不能因名称相同就静默合并。重复提交同一次导入操作须幂等。
- 未知或外部文件的 ID 不构成更新其他账号的权限；不能查询或覆盖他人记录，无法匹配当前账号的记录仅能作为重新分配 ID 的新增候选。
- 导出后记录又被另一端修改时，导入须提示版本冲突并保留待选择的内容，不直接覆盖新修改。
- CSV 中缺少某条已有记录不会触发删除；回收站中的记录也不能因导入旧 CSV 而被无提示恢复。
- 错误行不应造成无提示的部分导入。首版建议先修正所有错误后整体导入，最终处理方式在导入设计时确定。
- 游客导入只写本机，登录导入写入后端验证的当前账号；文件不携带有效的账号权限或登录凭据。
- 状态和持续天数等派生列可以导出，导入后由系统按日期重新计算，不能信任文件给出的状态覆盖业务规则。
- 导出范围为当前数据空间的全部已保存记录。登录账号有未提交草稿时提示先手动提交或另行保留；不把草稿悄悄混入“云端完整备份”，也不因导出而自动提交草稿。
- CSV 可用于外部整理和通用数据交换，不承诺兼容所有外部应用格式或原站特殊数据；原站适配另列为后续需求。

完整 JSON 导入导出为已确认的 P0：

- 网页可导出当前账号的完整 JSON 备份，包含格式版本、导出时间、日期规则、记录 ID、分类与配色、事项、重点日期及恢复所需元数据。
- 导出范围包含当前仍保留的回收站记录及其删除状态，已永久清理的记录不在导出范围内。
- 不导出密码或密码哈希、会话令牌、微信密钥等认证凭据；账号权限不能通过备份文件迁移。
- 导入前验证格式版本、日期及引用关系，预览新增、更新、重复、冲突与回收站数据的处理结果，用户确认后写入。
- 登录导入归属当前已验证账号，游客导入归属当前本机命名空间；不信任文件指定的所有者。重复导入去重，存在版本冲突时明确选择，不覆盖较新的修改。
- 默认保留当前账号中未出现在文件中的数据，导入旧备份不得静默恢复已删除事项；整份替换和清空现有数据不属于普通导入行为。
- 文件导出与服务端数据库备份分别提供：前者用于用户自行迁移和恢复，后者用于服务故障恢复。

### 6.8 原站专用迁移（后续候选）

- 已确认首版从空数据开始，专用迁移不阻塞上线；不删除旧站数据，也不自动切换旧域名。
- 当前取得的是源码副本，不能视为用户历史数据备份；旧站完整 JSON 导出和特殊格式适配待后续需要时开发。
- 通用 CSV 功能仍可用于导入符合新模板的数据，但不自动完成 ChatGPT 身份向微信身份的映射。
- 后续如实施迁移，应验证数据归属，检查事项、分类、配色与重点日期，保留原始文件和重试途径。
- 原站浏览器缓存受域名隔离，新站不能直接读取旧域名本机记录；不能按昵称或邮箱相似自动合并账号。

## 7. 存储结构、在线保存与跨端刷新

### 7.1 数据组织

首版使用 PostgreSQL 保存结构化记录，两端共用同一套业务表。以下为逻辑模型与建议表名，最终物理表、字段和索引需通过 Prisma 及认证最小验证后固定；不将讨论中的建议视为已完成建表。

| 分组 | 建议表名 | 职责与主要内容 |
| --- | --- | --- |
| 用户 / 认证 | `users` | 内部用户、显示名称、账号状态、创建时间、注销申请及到期时间；能否复用 Better Auth 用户表先验证 |
| 认证 | `auth_accounts` | Better Auth 登录凭据及密码哈希，不自行实现密码存储算法 |
| 认证 | `auth_sessions` | Better Auth 会话、所属用户、有效期；小程序会话如何统一需验证 |
| 认证 | `auth_verifications` | 邮箱验证和密码重置等临时验证记录，按所选版本生成 |
| 微信身份 | `wechat_identities` | 内部用户、应用标识、OpenID、可空 UnionID |
| 扫码请求 | `qr_requests` | 登录 / 绑定意图、原浏览器约束、短期状态、到期时间、确认用户和一次性消费状态 |
| 核心业务 | `categories` | 分类 ID、用户 ID、名称、颜色和版本 |
| 核心业务 | `entries` | 事项 ID、用户 ID、分类 ID、标题、起止日期、版本、创建 / 修改时间、删除及回收站到期信息 |
| 核心业务 | `entry_focus_days` | 事项 ID、重点日期及并发控制所需信息；同一事项同一天唯一 |
| 导入执行 | `import_jobs` | 游客 / CSV / JSON 导入的幂等标识、预览依据、状态、结果及必要的 ID 对应关系 |
| 账号合并 | `account_merges` | 来源 / 目标账号、预览依据、执行状态和恢复所需信息 |
| 合并映射 | `merge_record_mappings` | 来源记录与合并后记录的对应，供其他网页的旧草稿重新确认；物理上是否独立建表由技术设计决定 |

核心记录只有分类、事项、每日重点三类。回收站优先用事项软删除字段实现；统计、状态及持续天数动态计算，首版不另外建统计表。CSV / JSON 是交换格式，不将整个用户的数据作为一份 JSON 覆盖业务表。

工程约束：

- 分类和事项使用稳定 ID；新增可由客户端生成 UUID。后端验证归属，重试不能重复新建，也不能因 ID 相同而覆盖已有记录或他人记录。
- 关键可变记录保留服务器维护的版本，修改时原子检查基准版本；分类引用须同时验证属于同一用户。
- 微信身份对 `(app_id, openid)` 唯一；重点对 `(entry_id, date)` 唯一。建议按用户、日期范围及回收站到期时间建立必要索引，具体设计不要求用户逐项选择。
- 日期使用 `DATE`，操作时间使用 `timestamptz`；不在每个用户上引入可修改的时区设置。
- 认证表以所选 Better Auth 版本生成的模型为准；若业务用户与认证用户需分离，使用受控关联，不能先假定微信用户一定具有邮箱。
- 导入与合并保留可重试的幂等执行记录；预览后发生数据变化要重新检查，写入须有事务边界。必要的快照或映射可以使用受控 JSONB 字段，不因此改为整份用户 JSON 存储。

### 7.2 已登录账号的在线保存与 Web 草稿

- 服务器是已保存数据的统一来源。用户点击保存后立即调用业务 API，服务器确认成功才显示“已保存”；本机缓存和未提交草稿不构成云端保存成功。
- Web 已加载页面可查看本机缓存，编辑输入可暂存为草稿。断网、超时或保存失败时显示“尚未提交”，保留内容；恢复网络后由用户手动提交，不自动补传。
- 缓存是上次服务器数据的副本，草稿保存输入、目标账号 / 记录和原基准版本；与正式数据分开，刷新不能覆盖草稿，也不能悄悄把草稿基准更新成新版本后覆盖服务器。
- 网络恢复和前台定时刷新只自动拉取，不自动提交草稿。保存响应丢失时先核对服务器状态，不能直接宣称失败或无限重复创建。
- 小程序按在线使用设计，不要求已登录账号的离线新增、编辑、删除或自动补传；失败时明确提示并允许用户重试，不能显示成功。游客本机保存遵循第 5.7 节。
- 首次登录、加载云端数据和重新认证需要网络；缓存已加载内容不等于网页资源支持断网冷启动，PWA 不属于首版要求。
- 会话失效时保留 Web 草稿，重新登录同一账号后拉取最新记录，再手动提交。账号切换时缓存和草稿隔离，不能将 A 的输入提交给 B。

### 7.3 并发与冲突

- 即使两端始终联网，也可能同时编辑同一事项，因此保留基本版本检查。本节处理同一账号记录冲突，两个云端账号的身份及数据合并仍按第 5.6 节处理。
- 不同事项按各自 ID 和版本独立保存，不整份覆盖用户数据；后续完整刷新即可显示双方修改。
- 同一事项保存时发现服务器版本已变化，提示用户查看最新内容并保留草稿。首版不依赖完整离线同步引擎或自动三方合并；有可靠基准的独立字段合并可作为工程优化，不作为必须完成的复杂协议。
- 冲突界面按适用情况提供使用服务器内容、重新确认后提交草稿、另存一份；保留两份时显式新建事项，不将旧编辑当作无条件覆盖。
- 一端删除另一端仍在编辑时检查删除状态，保留草稿但不自动恢复事项；已永久清理的目标不得因旧缓存或旧请求重现。
- 重点按“设置为重点 / 取消重点”的明确目标处理，避免重试一次开关操作导致反向结果；不同日期的重点互不覆盖。
- 分类变更和删除不能产生指向不存在分类的事项；需要校验或明确处理。
- 修改失败、网络超时和服务器返回失败时不能显示已保存。普通记录重试使用稳定 ID 与版本检查，不要求增加通用的持久操作回执表。

### 7.4 日期与时区

- 事项起止日期和重点日期使用日历日期，格式为 `YYYY-MM-DD`，不按 UTC 时间戳换算后改变日期。
- 系统操作时间使用 UTC 保存。
- 已确认首版统一使用 `Asia/Shanghai`；“今天”、每日重点可选范围和以今天结束事项均按北京时间计算，确保不同设备一致。
- 海外服务器的系统时区及用户设备的时区不改变该业务规则；必要时在日期界面标明北京时间。
- 首版不提供账号时区修改；后续如增加自定义时区，须独立设计且不能静默改写历史事项日期。

### 7.5 首次完整加载、缓存与跨设备恢复

- 首次登录完整加载账号业务数据，包括分类、事项、重点及仍保留的回收站记录，不默认只缓存最近月份。完整缓存不意味着界面一次渲染全部事项或日期。
- 首版优先请求一致的完整数据集，失败可重试继续完成加载；确需分批时由技术设计处理进度和一致性，不引入常驻增量变更日志。加载期间其他端已确认的修改须在本次一致数据集或随后刷新中反映。
- 完整加载成功后更新该账号的本机缓存，下载中断不能把半份数据或空结果当作完整快照。未完成时显示加载状态，搜索和统计不将局部内容冒充完整结果。
- 网页少量草稿可用 localStorage；完整账号缓存建议用 IndexedDB。小程序使用平台持久存储适配；容量和写入失败需要验证，不能假定无限空间或缓存永不清理。
- 本机写入失败或容量不足时提示，不能假装游客数据或草稿已保存；不静默删除游客原始数据或未提交草稿来腾出空间。云端已保存与本机缓存可用状态分别显示。
- 同一微信身份在同一个日序小程序中换手机登录，仍关联原内部用户，重新加载服务器已确认的数据；网页使用原邮箱身份登录同理。
- 缓存丢失只触发重新加载，不新建业务账号、不向服务器提交空数据替换。只有服务器已确认的数据可恢复，未提交草稿和未上传游客数据不保证在本机清除后找回。

### 7.6 前台全量刷新与不引入 Redis 的边界

- 在首次加载后，持续前台约每 30 秒检查并拉取完整服务器数据；回到前台、恢复网络或手动刷新时立即拉取。后台停止轮询，恢复时补一次刷新，不承诺后台持续运行。
- 在线保存成功后更新本端视图和缓存；另一端在上述刷新时机看到结果，不承诺秒级实时推送。可以使用响应版本或 ETag 减少无变化传输，但不要求为此建立增量同步日志表。
- 同一客户端合并重叠刷新、避免旧响应覆盖新状态；失败允许退避重试。所有刷新均保留当前草稿及其原始基准，数据读取不能触发草稿写入。
- 首版不创建 `user_sync_state`、`sync_changes`，普通 CRUD 不依赖 `mutation_receipts`；不建设已登录账号的离线持久队列，也不通过上传整份本机缓存写回云端。
- 首版不使用 Redis。会话、验证和二维码状态可存在 PostgreSQL；到期任务扫描数据库执行，正确性由事务、唯一约束和幂等保证。普通限流可按单实例内存 / 数据库能力设计，具体参数另定。
- 后续只有实际出现多实例共享状态、缓存瓶颈或专用队列需求时，再独立评估 Redis；这不是当前实现前置条件。

## 8. 非功能需求

### 8.1 网络与体验

- 业务接口、网页核心静态资源由自有部署提供；日常记录和回看不请求 ChatGPT 服务。
- 微信身份校验等必要微信接口由后端接入；平台故障与日序业务故障有可区分的用户提示。
- 核心界面包含加载、空数据、网络失败、同步失败和冲突状态，弱网时避免反复阻塞整个页面。
- 网页适配桌面常见分辨率，小程序适配常见手机尺寸；配色以外也提供状态文字，按钮和弹窗可清楚操作。
- 已确认延续原站配色和生活记录的整体视觉风格；电脑端保留宽屏时间轴方向，小程序按触控、窄屏和横向时间轴分别组织布局。

首版建议验收数据集为单账号 1,000 条事项、10,000 条重点记录，20 个并发活跃用户，不将其直接视为用户配额或产品硬限制。目标为受控正常网络中常用列表读取和单事项保存 API 的 P95 响应不超过 1 秒；已完成首次加载的另一端回到前台后，目标为 5 秒内看到已确认更新。持续前台时按约 30 秒轮询间隔检查，再加请求耗时，不承诺持续打开时也总能在 5 秒内跨端可见。配置、网络及统计窗口需随压测记录，以上目标尚未验证。

首次完整加载耗时、完整刷新流量、本机存储占用和双端时间轴渲染需分别测量；完整缓存不代表一次性渲染所有记录。存储不足、未完成加载和未提交草稿需要清楚可见，避免误判为数据丢失或保存成功。

### 8.2 数据保护与可恢复性

- 使用 HTTPS；网页登录会话使用适当的安全 Cookie，小程序按平台能力保护本系统会话。
- 普通用户仅可访问自己的数据；前端隐藏其他用户入口不构成权限控制。
- 登录、扫码确认和数据导入接口设定合理的频率及体积限制；令牌、微信密钥和完整私人记录不写入普通运行日志。游客原始数据、账号缓存及草稿按数据空间隔离。
- 数据库数据存放在持久化卷，容器重建不丢失记录；数据库默认不直接暴露到公网。
- 首版建议每日自动备份、至少保留 7 天，并保存一份服务器之外的副本；上线前完成一次恢复演练。
- 用户导出与服务端备份各自独立；前者便于个人迁移，后者用于恢复服务。

### 8.3 可维护性与发布

- 公共业务规则、接口契约和平台适配器分开维护，避免在公共规则中散落平台判断。
- 后端输入校验、跨用户隔离、重复请求、版本冲突、扫码登录状态、导入及合并幂等需要自动化测试；网页验证恢复网络和轮询不会自动提交草稿。
- 网页与小程序分别执行构建和核心流程验证，共享包改动须同时检查两个客户端。
- 通过数据库迁移管理结构变更；发布前有备份与兼容策略，旧版客户端仍可访问兼容接口。
- 小程序和网页分开发布，不因网页更新强制要求小程序同时通过审核。

## 9. 首版验收标准

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 小程序首次与重复登录 | 首次建立账号，再次登录得到同一内部用户，无重复账号 |
| AC-02 | 网页扫码确认 | 小程序确认后，原网页进入同一账号并加载相同数据；仅扫描不自动登录 |
| AC-03 | 扫码过期、取消、重放 | 不能建立网页会话，可提示并重新发起；其他浏览器不能领取会话 |
| AC-04 | 事项完整流程 | 两端均可新建、编辑、结束及移入回收站，日期校验一致，删除有确认 |
| AC-05 | 日期边界 | 同日起止计 1 天，跨月和闰日计算正确，未来事项状态正确，区间包含首尾 |
| AC-06 | 每日重点 | 同一事项不同日期独立标记，同一天去重；未来及区间外日期不可标记 |
| AC-07 | 编辑范围影响重点 | 缩短范围前列出受影响重点，用户取消时数据不变，确认后两端一致 |
| AC-08 | 分类管理 | 改名与改色作用于相关记录；删除分类后事项进入回收站且旧期限不重置；分类顺序持久化；最后一个分类不可直接删除 |
| AC-09 | 账号隔离 | 用户 A 无法通过修改记录 ID、分类 ID 或请求参数读取或更改用户 B 数据 |
| AC-10 | 正常跨端同步 | A 端保存成功后，B 端进入前台并刷新可见同一修改；符合约定测试环境下的同步目标 |
| AC-11 | Web 断网与手动提交 | 已加载页面可读缓存，未提交输入可暂存为草稿并显示尚未提交；恢复网络只刷新，必须由用户手动保存；不要求小程序登录账号离线记录或网页断网冷启动 |
| AC-12 | 并发和重试 | 新增重试不生成重复记录，旧版本更新不能覆盖新内容；不同事项独立保存，同一事项版本冲突时保留草稿并明确处理；不依赖离线自动合并引擎 |
| AC-13 | 删除传播 | 一端删除后另一端更新，旧缓存不会无提示恢复记录；删除与编辑并发进入冲突处理 |
| AC-14 | 普通账号切换 | 切换账号不泄露上一账号缓存与草稿，不将 A 的草稿提交给 B；受验证的账号合并按 AC-22 单独处理 |
| AC-15 | 查询与完整时间轴 | 网页与小程序均支持月、季度、年及全部时间范围，正确展示事项跨度及重点；筛选规则一致，小程序横向滚动、定位今天和触控操作可用 |
| AC-16 | CSV 导入导出 | 下载模板，新增及更新预览后确认；修改导出 CSV 中带原 ID 的行可更新对应事项，无 ID 的行可新增，重复项和版本冲突有提示，文件缺少行不删除原记录 |
| AC-17 | CSV 异常与归属 | 无效日期、无效重点范围及格式错误按行提示；校验失败不静默部分写入，文件不能指定导入他人的账号 |
| AC-18 | 独立部署与恢复 | 自有服务器可运行全部业务；重新创建容器不丢数据，可用备份恢复；不依赖 ChatGPT 运行时 |
| AC-19 | 公开注册 | 未获邀请的新用户可使用最终确定的公开登录入口建立账号；新账号的数据独立，异常登录与重复请求不会产生重复用户 |
| AC-20 | 绑定与登录意图区分 | 未被占用的身份经确认后关联当前账号，不生成多余空账号；登录另一个账号仅切换会话，不自动迁移数据 |
| AC-21 | 双账号数据合并 | 验证双方身份后显示预览，确认后保留双方独有内容；同名事项不直接合并，无法判定的差异保留两份；取消不改变双方数据 |
| AC-22 | 合并后的草稿恢复 | 合并可重试且不会部分完成；其他网页的来源账号草稿保留，在重新认证并取得后端映射后重新核对记录及版本，由用户手动提交或处理冲突，不自动补传 |
| AC-23 | 邮箱密码完整流程 | 新用户可独立邮箱注册，完成验证后登录；未验证时可重发验证邮件；忘记密码可申请重置、设置新密码并再次登录；会话与退出按既定策略处理 |
| AC-24 | 回收站与恢复 | 删除后正常视图隐藏，30 天内可恢复事项及重点；可确认后提前清空，到期自动清理；两端删除和恢复一致，旧缓存不擅自恢复或再次删除记录 |
| AC-25 | 统一北京时间 | 在系统为 UTC 的服务器及不同时区的设备上，同一时刻两端的今天、重点范围、结束日期和日期跨度一致，均按 Asia/Shanghai 计算 |
| AC-26 | 完整 JSON 备份 | 导出并导入备份可保留支持的事项、分类配色、重点日期和回收站状态；格式不兼容或引用无效时提示，导入需预览确认且不改变数据归属，不包含认证凭据 |
| AC-27 | 游客完整使用 | 两端不登录可管理本机事项、分类、重点和回收站，使用回看、搜索、统计及完整时间轴；本机保存后重进可读，网页可导入导出本机文件 |
| AC-28 | 游客登录接入 | 云端空则直接接入，已有数据则先预览合并；取消不丢本机数据，服务器确认完成前保留原始数据，失败或响应丢失后重试不重复导入 |
| AC-29 | 换设备与缓存丢失 | 同一微信身份登录同一小程序或同一邮箱登录网页，关联原内部用户并取回服务器已确认的数据；空缓存不触发云端删除，不承诺恢复从未上传的本机内容 |
| AC-30 | 完整加载与刷新 | 首次完整加载分类、事项、重点和仍保留的回收站；中断可重试完成，半份数据不作为完整快照，之后全量刷新反映其他端新增、修改和删除 |
| AC-31 | 前台轮询与恢复 | 持续前台约每 30 秒检查，回前台或恢复网络立即拉取，后台停止轮询；重叠及旧响应不覆盖新状态，刷新不提交或覆盖草稿 |
| AC-32 | 草稿与正式数据区分 | 服务器确认前不显示已保存；本机草稿携带原账号、记录和基准版本，刷新不悄悄更新提交基准，导出云端完整备份不混入未提交草稿 |
| AC-33 | 注销与撤销 | 两端重新验证后可自助申请，显示 7 天到期时间；窗口内明确撤销，普通登录不自动撤销；到期清理可重试，旧会话和旧草稿提交不能复活账号 |
| AC-34 | 本机存储异常 | 游客数据、缓存或草稿写入失败 / 容量不足有提示，不伪装已保存，不静默删除游客原数据或草稿；云端保存状态与本机缓存状态可区分 |

## 10. 实施顺序

### 阶段一：账号与双端最小闭环

- 初始化仓库、两个前端工程、后端和共享包。
- 建立统一用户、微信身份关联、会话和数据库迁移。
- 完成 Better Auth 与 NestJS、Prisma 的最小集成验证，确认无邮箱微信用户的映射，以及网页 Cookie / 小程序会话适配。
- 完成网页邮箱注册、验证、密码登录与重置，接入 Resend 并验证真实邮件投递；完成小程序登录和网页扫码确认，区分登录与绑定意图。
- 验证游客本机保存、一条事项在线新建及另一端完整读取；Web 草稿暂存后必须手动提交，不搭建离线队列或 Redis。

阶段出口：游客记录可靠保存，真实用户能在两端登录同一账号并读取同一条服务器记录；不要求先完成全部界面，平台实际能力和认证兼容性仍需实际验证。

### 阶段二：核心记录与跨端刷新

- 完成事项、30 天回收站与恢复、分类、每日回看、重点、搜索、统计和双端时间轴。
- 完成账号绑定、双账号数据预览与合并，以及合并后的会话和缓存恢复。
- 完成游客登录接入、首次完整加载、前台约 30 秒全量刷新、Web 缓存与草稿手动提交。
- 完成稳定 ID、版本冲突检查、保存状态、删除及回收站刷新；不建设增量日志和自动补传。
- 完成自助注销、7 天内撤销、到期清理和多设备会话处理。
- 完成账号隔离及双端业务一致性验证。

### 阶段三：数据交换与公开上线

- 完成通用 CSV 模板、新增与更新校验、预览、去重、版本冲突处理和导出；同时完成完整 JSON 导入导出及恢复校验。
- 验证登录异常、弱网、保存响应丢失、刷新不自动提交、存储不足、首次加载与全量刷新性能，以及备份恢复。
- 按发布要求提交小程序审核，部署正式服务。
- 正式版本面向所有人开放注册，原站专用迁移和邀请制不作为前置步骤；原站数据保留。

## 11. 后续候选需求

- 手机网页首次登录的备用方式、完整手机网页适配。
- PWA 页面资源缓存与离线冷启动。
- 登录账号的正式离线记录、自动补传、增量同步或实时推送，仅在以后重新确认需求后评估。
- 手机号等更多登录方式，以及多个邮箱或多个微信的复杂绑定组合。
- 更多统计、年度回顾和个性化设置。
- 原站专用数据迁移与历史身份归属确认。
- 如后续取得相关权限，再增加官方网页微信 OAuth 登录。
- 根据实际并发、故障恢复和运营需要评估 Redis、专用任务队列、监控及运营后台。

上述候选需求需另行明确范围和验收标准，不能自动纳入首版。
